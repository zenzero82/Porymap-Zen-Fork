The Porymap Studio foundation is now complete.

The repository currently has:

* Working native C++17/Qt/qmake Porymap fork
* Porymap Studio branding
* Existing Porymap functionality preserved
* Linux build verified
* Windows build verified
* Windows headless startup smoke test verified
* GitHub Actions working

* Architecture and technical documentation already written

We are now beginning actual Porymap Studio feature development.

# PRIMARY GOAL

Implement the foundations required for:

**Full Map Image → Metatile Matching → Automatically Generated Porymap Map**

This task will implement the first two components:

1. **New Map From Image**
2. **Deterministic Metatile Rendering Service**

Do NOT implement image-to-metatile matching yet.

At the end of this task, Porymap Studio should be capable of:

1. Loading a compatible Gen 3 project.
2. Opening **File → New Map From Image…**
3. Selecting a PNG.
4. Previewing the image.
5. Selecting primary and secondary tilesets.
6. Determining the image/map dimensions.
7. Validating the image against the expected metatile grid.
8. Rendering every available metatile from the selected tilesets into deterministic in-memory images.
9. Reporting that the image and selected tilesets are **Ready for Matching**.

# PART 4 — IMAGE ANALYSIS SERVICE

Create a Studio-specific service/class such as:

`MapImageAnalyzer`

Place it within the existing Studio module architecture.

The dialog should NOT contain the core image-analysis logic.

MapImageAnalyzer should support:

* Loading PNG
* Verifying the file exists
* Verifying Qt can decode it
* Reading exact pixel dimensions
* Retaining original image data
* Determining proposed map dimensions
* Validating alignment with the map/metatile grid
* Returning useful validation results
* Returning useful error messages

Do not silently crop images.

Do not silently resize images.

Do not alter pixels during analysis.

# PART 5 — DETERMINISTIC METATILE RENDERING SERVICE

This is the most important backend component in this task.

Create a Studio service such as:

`MetatileRenderService`

Its purpose is to generate a deterministic image representation for every metatile available from the selected primary and secondary tilesets.

DO NOT duplicate Porymap's graphics logic if an existing rendering path can be reused.

Reuse the same:

* Tiles
* Palettes
* Metatile definitions
* Layer information
* Flip flags
* Transparency behavior
* Primary/secondary tileset behavior

that Porymap itself uses when displaying a map.

The goal is:

Given:

* project
* primary tileset
* secondary tileset
* metatile ID

Return:

* deterministic image
* metatile ID
* source tileset information

Conceptually:

```text
Metatile 0x000 → QImage
Metatile 0x001 → QImage
Metatile 0x002 → QImage
...
```

The output images must be suitable for future pixel-level comparisons.

---

# PART 6 — PIXEL ACCURACY REQUIREMENTS

This renderer is NOT intended primarily for UI thumbnails.

It will become the reference library used by the image-matching engine.

Therefore:

* Do not apply smoothing.
* Do not use lossy conversion.
* Do not scale unless absolutely necessary.
* Preserve exact RGB/RGBA output.
* Use deterministic rendering.
* Ensure the same metatile always produces identical pixel data given the same project assets.
* Respect transparency exactly as Porymap does.

If Porymap's existing renderer produces a composited result dependent on surrounding blocks, identify this limitation clearly.

We need the closest deterministic representation of what a standalone map block visually produces.

---

# PART 7 — PRIMARY + SECONDARY TILESET HANDLING

Porymap maps can use primary and secondary tilesets.

The service must correctly understand the metatile ID ranges and ownership rules used by Porymap.

Do NOT assume arbitrary ID ranges.

Use Porymap's existing constants/models.

The result should make it possible to ask:

```text
What are every available metatile and rendered image
for this primary + secondary tileset combination?
```

Return a collection suitable for later matching.

For example conceptually:

```text
RenderedMetatile
{
    metatileId
    sourceTileset
    image
}
```

Use C++/Qt structures appropriate to the existing project rather than blindly copying this pseudocode.

# PART 10 — PERFORMANCE

Do not prematurely over-optimize, but avoid obviously inefficient architecture.

The future matcher may compare thousands of image cells against hundreds of metatiles.

For this task:

* Render each unique metatile once per analysis.
* Cache results for the selected tileset combination where reasonable.
* Invalidate the cache if relevant tileset data changes.
* Do not repeatedly render the same metatile for every image cell.

The future matching engine should be able to consume the already-rendered collection.
